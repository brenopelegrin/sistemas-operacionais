# Projeto pytasks

Este projeto consiste em um backend escalável para execução de tarefas em workers. Ele é composto por uma "api", que recebe as requisições usando Flask e as publica em uma fila AMQP usando Celery, e um "handler", que utiliza Celery para executar as tarefas recebidas da fila AMQP.

## Visão Geral do Projeto

`pytasks` é um microsserviço completo e personalizável para executar tarefas computacionais em máquinas remotas e visualizar seus resultados através de uma API. O objetivo principal é tornar a computação em nuvem mais acessível, permitindo que os desenvolvedores se concentrem apenas no desenvolvimento das tarefas, e não no backend que as executa.

O projeto é baseado em tecnologias robustas como:
- **API**: Construída com [Flask](https://github.com/pallets/flask) e servida com [Gunicorn](https://github.com/benoitc/gunicorn).
- **Handler**: Construído sobre [Celery](https://github.com/celery/celery), utilizando [RabbitMQ](https://www.rabbitmq.com/) ou [Redis](https://redis.io/) como broker de mensagens e [PostgreSQL](https://www.postgresql.org/) para armazenamento dos resultados das tarefas.

### Arquitetura

A arquitetura do `pytasks` envolve dois componentes principais:

1.  **API**: Expõe endpoints HTTP para que os usuários possam enviar requisições de tarefas para uma fila.
2.  **Handler**: Escuta a fila de mensagens, executa as tarefas recebidas e armazena os resultados em um banco de dados.

## Como fazer build

Para construir as imagens Docker do projeto, certifique-se de ter o `docker-compose` (versão 2.19.0 ou superior) instalado.

É necessário ter `docker-compose` 2.19.0 ou superior pois esse projeto utiliza o recurso de `additional_context` para fazer o build dos serviços utilizando os containers já criados nos checkpoints 1, 2 e 3.

Execute o seguinte comando na raiz do projeto:

```bash
docker compose build --no-cache
```

### Processo de Build do Docker Compose

O `docker-compose.yml` define vários serviços, incluindo `api`, `handler`, `rabbitmq` e `postgres`. Um aspecto importante do processo de build é a utilização de estágios de build multi-stage e contextos adicionais para o serviço `handler`.

-   **Serviços `checkpoint1`, `checkpoint2`, `checkpoint3`**: Estes serviços são definidos para construir imagens a partir de contextos externos (`../../checkpoint1/`, etc.). Eles são usados como estágios de build para o `handler`.
-   **Serviço `api`**: A imagem da API é construída a partir do `Dockerfile` localizado em `./api`. Ele instala as dependências Python e configura o Gunicorn para servir a aplicação Flask.
-   **Serviço `handler`**: A imagem do handler é construída a partir do `Dockerfile` localizado em `./handler`. Este `Dockerfile` utiliza um build multi-stage, copiando binários e dependências dos estágios `build_checkpoint1`, `build_checkpoint2` e `build_checkpoint3` (que correspondem aos serviços `checkpoint1`, `checkpoint2`, `checkpoint3` definidos no `docker-compose.yml` através da opção `additional_contexts`). Isso permite que o handler inclua binários específicos necessários para a execução de certas tarefas.

## Como Executar

Após construir as imagens, você pode iniciar os serviços usando o Docker Compose. Antes de rodar, é necessário exportar as chaves JWT para autenticação.

```bash
export JWT_PRIVATE_PEM=$(cat ./examples/keys/jwtRS256.key) && \
export JWT_PUBLIC_PEM=$(cat ./examples/keys/jwtRS256.key.pub) && \
docker compose up -d
```

Este comando iniciará os contêineres em modo detached (segundo plano). A API estará disponível em `http://localhost:8080`.

**Atenção**: Este comando utiliza um par de chaves RSA de exemplo e senhas padrão para PostgreSQL e RabbitMQ. Em um ambiente de produção, é **IMPRESCINDÍVEL** configurar suas próprias chaves RSA e credenciais para evitar problemas de segurança. Consulte a seção de configuração para mais informações.

## Como Configurar

As variáveis de ambiente para os serviços `api` e `handler` podem ser configuradas de diversas maneiras, sendo o uso de arquivos `.env` a forma recomendada.

## Endpoints da API

A API do `pytasks` expõe os seguintes endpoints:

| Endpoint                | Método   | Descrição                                        |
| :---------------------- | :------- | :----------------------------------------------- |
| ``/task``               | ``POST`` | Envia uma nova tarefa para o servidor.           |
| ``/task/<string:task_id>`` | ``GET``  | Busca informações de uma tarefa específica.      |
| ``/tasks``              | ``GET``  | Lista todas as tarefas disponíveis.              |
| ``/ping``               | ``GET``  | Verifica a saúde da API.                         |
| ``/protected``          | ``GET``  | Retorna o payload decodificado do token JWT, se válido. |
| ``/token``              | ``GET``  | Gera um token JWT para autenticação.             |

### Exemplos de Requisições

#### Enviar uma Nova Tarefa (`POST /task`)

Este endpoint registra uma nova tarefa no servidor. Você precisa passar alguns argumentos obrigatórios dentro de um `application/json`. O JSON deve conter uma string com o tipo da tarefa, nomeada `type`, e os argumentos específicos da tarefa como um dicionário, nomeado `args`.

**Exemplo de Requisição (tarefa de adição):**

```json
{
    "type":"add",
    "args": {
      "x": 1,
      "y": 2
    }
}
```

```bash
curl -X POST http://localhost:8080/task -H 'Content-Type: application/json' -d '{"type":"add", "args":{"x": 1, "y": 2}}'
```

**Exemplo de Resposta:**

```json
{
  "id": "5861c3a8-fa0f-4b84-9e54-04b545408114",
  "result": {},
  "args": {"x": 1, "y": 2},
  "status": "PENDING",
  "type": "add"
}
```

#### Visualizar o Status de uma Tarefa (`GET /task/<task_id>`)

Este endpoint retorna os dados atuais para a tarefa com o ID `task_id` em formato `application/json`.

**Exemplo de Requisição:**

```bash
curl -X GET http://localhost:8080/task/5861c3a8-fa0f-4b84-9e54-04b545408114
```

**Exemplo de Resposta:**

```json
{
  "id": "5861c3a8-fa0f-4b84-9e54-04b545408114",
  "result": 3,
  "args": {"x": 1, "y": 2},
  "status": "SUCCESS",
  "type": "add"
}
```

O status de uma tarefa recuperada pode ser:
-   `PENDING`: Significa que a tarefa não existe *OU* existe e ainda não foi recebida por um worker.
-   `STARTED`: Significa que a tarefa foi recebida por um worker e está sendo computada.
-   `SUCCESS`: Significa que a tarefa foi recebida por um worker, já foi computada e está disponível para visualização.

#### Gerar Token JWT (`GET /token`)

Este endpoint gera um token JWT para autenticação. Requer `user` e `password` como parâmetros de query.

**Exemplo de Requisição:**

```bash
curl -X GET "http://localhost:8080/token?user=your_username&password=your_password"
```

**Exemplo de Resposta:**

```json
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "exp": 1678886400
}
```
